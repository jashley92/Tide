# Option E build plan

Working plan for the `ux/option-e` branch. It turns the option E mockups into shipped pages, in small steps that
can each be checked against what they were meant to change. This file is a working document: remove it, or fold what
lasts into the product and architecture docs, before the branch merges to `main`.

## The brief

This is the request the plan answers, written out in full so that every session and subagent working on it starts
from the same understanding.

**Goal.** Make the analyst's day in TIDE (triage, write, order, present, send, then follow the actions) take fewer
page changes, less scrolling and fewer clicks, without asking the team to relearn the application.

**Who it is for.** A small threat intelligence team that prepares one brief a day against a fixed meeting time. They
work on laptops at about 1920×1080, keyboard first, and present on a shared screen to people who also join from
their own machines.

**What option E is.** Today's pages and sidebar, refined in place, with one context rail on the right of every page
in place of the one-off side panels each page has grown. Present mode keeps today's deck: everything the meeting
needs (slide content, action cards, indicators, tags, who is here, whose hand is up) is on the shared screen for
everyone, and a presenter-only rail holds only the controls that are the presenter's.

**Principles, in priority order.**

1. *Never widen who sees something.* TLP markings, edition ceilings and the presenter-only boundary are safety
   properties. No change may show restricted content to a wider audience, and every new action that changes data is
   permission-checked, concurrency-checked and audited like the existing ones.
2. *The answer before the detail.* A page states what needs a decision first (what is exploited, what we run, what
   has no owner), and puts the fix next to the warning.
3. *Context comes to the analyst.* Selecting something shows what TIDE already knows about it in the rail. The
   analyst does not leave the page to find out.
4. *Familiar first.* Routes, names, keys and page layouts stay unless a finding justifies the change. Every key that
   works today works afterwards.
5. *One pattern, not eight.* The rail, the selected-row behaviour and the "next step" line are built once and
   reused.

**How the work is done.**

- Each change starts from a written *intended effect*: one sentence saying what a person will see or be able to do
  afterwards that they could not before. The change is not finished until that sentence has been checked in the
  running application by someone other than its author.
- Independent work goes to subagents, each in its own worktree, with a brief that names the files, the intended
  effect and the checks. Two writers never touch the same file at the same time.
- `/simplify` runs on every change before review, and again on each phase as a whole.
- Nothing merges with a failing test, a failing layout check or an unexplained visual difference.

**Done means** an analyst can run the day in the mockup's workflow on a seeded instance at 1920×1080, 1440×900 and a
narrow window; every existing test and guard passes; the new behaviour has tests and layout rules of its own; and
the documentation and its screenshots describe what shipped.

### Where the mockups were wrong

- The editor mockup shows "All changes saved". The editor has no autosave today; item 3.9 adds it.
- The Present mockup says notes are "only yours until the meeting ends". Notes are shared by the team and stay
  shared (decision 4). The rail shows the team's notes for the article.
- The Actions mockups show counts on every tab at no cost. They need a new query.

One more item in this phase is not a rail change:

| # | Change | Effect | Checks |
|---|---|---|---|
| 3.9 | Autosave in the article editor, after 3.3. A pause in typing saves the form; the bar says "Saving…", then "Saved at 10:12", or what stopped it. | An analyst who closes the tab or loses the connection loses at most a few seconds of typing. | See below. |

Autosave touches three safety properties, so its pull request settles each before any code:

- **Concurrency.** Every save is checked against the edit version, as today. When a colleague has saved meanwhile,
  autosave stops and says so; it never overwrites and never merges silently.
- **Markings.** A change to a TLP marking, or any change that would put a part into the company-wide edition, is
  not autosaved. It waits for an explicit Save, so a slip of the hand cannot widen an audience.
- **Audit and history.** Autosaves within one editing session collapse into one history entry, so the article's
  history stays readable. An article already on a sent brief is not autosaved at all: corrections stay deliberate.

It also has to keep `UnsavedGuard` honest (nothing unsaved means no prompt), survive a dropped circuit, and stay
off for people reviewing an article they cannot edit.

## How each change is verified

The same loop for every pull request, so that "it compiles and the tests pass" is never taken for "it does what we
meant".

1. **State the effect.** The pull request description opens with the intended effect from this plan, and lists
   what must *not* change (other pages, other roles, the other edition).
2. **Write the check first where one can exist.** A layout rule in `layout.mjs`, an integration test on the markup,
   or a unit test on the service. Run it and see it fail.
3. **Implement**, in a worktree, touching only the files named in the brief.
4. **Run the guards:** `dotnet test`, `node tools/screenshots/layout.mjs`, `tools/ci/check-removed-css.sh`.
5. **Simplify:** `/simplify` on the diff; re-run the guards.
6. **Verify the effect independently.** A different subagent, given only the intended effect and the running
   application (not the diff), loads the page at 1920×1080, 1440×900 and 780 wide, in both themes, and for Present
   as both presenter and follower. It reports: effect seen or not, with a screenshot; anything that changed and was
   not meant to, found by comparing against the baseline.
7. **Check the boundary** whenever TLP, editions or presenter-only content is involved: as a user limited to the
   company-wide edition, and as a follower, confirm nothing new is visible.
8. **Review** the pull request. Only then merge into `ux/option-e`.

At the end of each phase: `/simplify` and `/code-review` on the phase as a whole, a full layout run, and a
walkthrough of the day on the seeded demo.

## How subagents are used

| Role | Used for | Given | Not given |
|---|---|---|---|
| Explore | Mapping a page before its change. | The question and the files. | Write access. |
| Implement | One pull request, in its own worktree. | The intended effect, the named files, the checks to write first, this plan's rules. | Other pull requests' files. |
| Verify | Step 6 above. | The intended effect, the baseline, the running application. | The diff or the implementer's summary, so it cannot simply agree. |
| Review | `/code-review` at the end of a phase. | The phase's diff. | |

Files that many changes touch are owned by one writer at a time: `app.css` (each change adds to its own section),
`MainLayout.razor`, `BriefPage.razor`, `Triage.razor`, `ArticleEditorPanel.razor`, `Present.razor`, `present.js`
and `layout.mjs`. Phase 2 items are safe to run in parallel in threes; phase 3 and phase 4 items that share one of
these files run in sequence.

## Branches

- `ux/option-e` is the integration branch, cut from `main`. It is rebased on `main` at the start of each phase.
- Each numbered item is a short branch `ux/e-<number>-<slug>` and one pull request into `ux/option-e`.
- Phases 1 to 3 can merge to `main` phase by phase once verified, because each leaves the application whole.
  Phase 4.6 stays behind its setting until rehearsed.
